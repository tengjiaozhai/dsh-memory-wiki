# 从零构建一个简单的 LLM Wiki

> 目标：一个 agent 能在 5 步内搭起来、且三个月后不烂的最小知识库。
> 实例全部取自 `/Volumes/PortableSSD/docs/tengjiaozhai.github.io`（下称「本仓」），尺寸为 2026-10-22 实测。

## 何时用这篇

- 用户说「我也想搭一个自己的 wiki」「把笔记整理成知识库」「从零开始」
- 已有大量笔记但 wiki 层为空，需要从 0 到 1（不是从 1 到 N，那是 compile）
- 要评估一套现成 wiki 的结构是否合理

## 一句话方法

LLM 不当作者，只当索引员。你只需要给它四样东西：**目录骨架 + 两个结构文件 + 一份 schema + 两个脚本**。
页面是这四样长出来的产物，不是起点。

## 0. 先定三件事（定错要返工）

| 决定 | 影响 | 本仓的答案 |
|---|---|---|
| raw 放哪、能不能改 | 决定 digest 策略与写权 | 自有笔记就在仓库根目录 + `thoughts/`，路径冻结；外部裁剪进 `raw/articles/`，不可改 |
| 规模目标 | 决定要不要向量检索 | 目标数百页以内，只要 `index.md`，不上 embedding |
| 谁读它 | 决定要不要上站、能不能用 `[[…]]` | 只有人和 agent 读，不进站点，双链可以放心用 |

第三行最容易忽略：**一旦进站点，双链和内部小节锚点全部受渲染器约束**，代价陡增。

## 1. 目录（先建最小的）

```text
my-wiki/
├── AGENTS.md            # schema：唯一的行为约束（Claude Code 用 CLAUDE.md）
├── raw.md / *.md        # raw：你自己的笔记，路径冻结
├── raw/articles/        # raw：外部裁剪（可选，有外部资料才要）
├── tools/
│   ├── wiki-index.mjs   # 重建 index 的自动段
│   └── wiki-lint.mjs    # 只读健康检查
└── wiki/
    ├── index.md         # 内容导向目录（自动段 + 手写段）
    ├── log.md           # 时间导向记录（追加式）
    ├── sources/         # 一份 raw 资料一页
    ├── concepts/        # 可复用的机制/判断（出口）
    ├── entities/        # 有名有姓的东西（后加）
    ├── synthesis/       # 跨来源对比与决策（后加）
    └── outputs/         # 成品索引（后加）
```

**先只建 `index.md`、`log.md`、`sources/`、`concepts/` 四处**。`entities/`、`synthesis/`、`outputs/` 等真的有内容再建——空目录会诱导你为了填满它而造空壳页。

## 2. 两个结构文件，先写它们，不要先写页面

### index.md

内容导向，是 LLM 每次回答前的定位入口。必须给**自动段与手写段的分界线**，否则重建脚本会吃掉手写内容：

```markdown
# Wiki Index

> 最近更新：YYYY-MM-DD · 共 N 个内容页

## Sources
- [[wiki/sources/xxx|标题]] · note · 4000 行 · verified

<!-- wiki-index:auto-end -->

## 待建页面        ← 手写段：有证据但还没成页的候选

## raw 摄取状态    ← 手写段：必需，否则下次会话不知道还有多少没消化
```

手写段里最值钱的是 **「待建页面」**：它是人工版的「知识空白清单」，防止每次都重新发现同一个缺口。

### log.md

```markdown
## [YYYY-MM-DD] <op> | <标题>
```

- 行首、方括号内**只放日期**（带时刻会让 grep 脚本失配）
- `op` 用固定白名单：`ingest` / `query` / `lint` / `save` / `schema`（本仓多加一个 `compile`）
- 正文必须含 `新增` / `touched:` / `冲突:` 之一，否则这条记录没有可检索信息
- 只追加、不回改；写错就追加一条修正

## 3. schema 写什么（第一版 150 行就够）

六节，按顺序写：

1. **定位**：这个库要回答哪三类问题、价值判据是什么（不是目录说明）
2. **三层与写权**：raw / wiki / schema，谁写哪层、能不能改
3. **目录**：一页树 + 每一处的一句职责
4. **页面类型**：每类一页模板（frontmatter 字段 + 固定小节名）
5. **硬规则**：双链格式、命名、一概念一页、冲突不覆盖、证据可追溯
6. **操作**：ingest / query / lint 各几步，每步的产物

后面再单独加 `index.md` 与 `log.md` 的格式节——因为这两个文件是**程序要解析的**，格式必须写死。

本仓 `AGENTS.md` 现为 632 行，但第一版不需要这么多：把第 5、6 节写清就能跑，其余随实践长。**不要一次写全**，没被违反过的规则不值得写。

## 4. 两个脚本，职责要分清

| 脚本 | 本仓行数 | 职责 | 绝对不要做 |
|---|---|---|---|
| `wiki-index.mjs` | 162 | 扫 frontmatter 重建 index 的**自动段**，保留标记之后的手写段；默认干跑，`--write` 才落盘 | 不要碰手写段，不要改页面 |
| `wiki-lint.mjs` | 273 | 只读体检：断链 / 孤儿页 / frontmatter 缺失 / digest 漂移 / 重复概念 / 过期；`--only` 过滤 | **绝不自动改文件**，也不要为了「通过」而放宽检查 |

两个共同原则：

- 脚本只做**机器能判的**（是否存在、是否相等）。判断类问题（这页该不该建）留给人和 LLM。
- 脚本用 `dirname(import.meta.url)` 定位仓库根，从任何 cwd 都能跑——这样它能当 skill 的常驻工具，不必 `cd`。

## 5. 灌第一批（顺序不能反）

1. 扫 raw 的小节标题：`rg "^## " *.md`，产出「主题 → 出现篇章」矩阵
2. 主题在 **≥2 篇** raw 出现 → 才是 concept 候选；只出现 1 次 → 写进 source 页的「本篇独有」
3. 一 raw 一 source 页，四节：这一篇覆盖什么 / 可抽出的原子 / 与其他笔记的重叠点 / 本篇独有
4. 每个 concept 页的验收：**至少 3 个断言能落到 ≥2 篇 raw 的具体标题**。做不到就不建
5. 建 index（`wiki-index.mjs --write`）→ 跑 lint → 写第一条 log

第 4 步是这套方法的分水岭。跳过它的后果不是「不完整」，而是「一堆两句话的空页」，而空页会让后来的会话反复重读、反复补写。

## 6. 三个验收（都要能复跑）

1. `node tools/wiki-lint.mjs` → 0 项
2. `node tools/wiki-index.mjs --write` 连跑两次，第二次 `git diff` 为空（幂等）
3. 随手挑一个概念问题，2 跳内能到证据：`index` → `source` 页 → raw 的**文件 + 标题文本**

## 7. 三个顺序不能颠倒（本仓踩过的坑）

| 先定 | 否则 |
|---|---|
| index 的 `auto-end` 标记 | 第一次 `--write` 就把手写的「待建页面」冲掉 |
| digest 口径 `split('\n').length` | 与 `wc -l` 差 1，全库 source 页要重算一遍 |
| 「不链 raw 内部小节」 | 站点 TOC 用序号锚点，插一节后面全漂，返工量随页数放大 |

另外一条不是顺序问题、但同样致命：**source 页写「发掘与分流」，不写摘要**。原文若是你自己写的结论，再摘一遍等于复述。

## 8. 什么规模加什么（别提前）

| 规模 | 加什么 | 依据 |
|---|---|---|
| ≤ 约 100 来源、数百页 | 只用 `index.md` 导航 | 这是该模式的舒适区，此时上 embedding 是过度工程 |
| 页数接近上限 | 全文搜索（BM25 或向量） | 先加搜索，不要先加图分析 |
| 出现「我记得写过但搜不到」 | 相关性排序（多信号加权） | 排序问题不是存储问题 |
| 多个主题域并行推进 | 把「意图」从 schema 里拆出去单独成文件 | 一页定位装不下分叉方向时再拆 |

## 9. 常见退化（出现任一就停下来）

- **空壳 concept**：两句话、无实例、无取舍
- **平行概念页**：同一概念两页（新建前先 grep 一遍 index 与目录）
- **孤儿 source 页**：不被任何 concept 引用，等于只有入口没有出口
- **摘要式 source 页**：复述原文而非分流原子
- **计数写进文档**：目录树注释里写「42 个 source 页」，几天后必错。计数只该有一个出处（index 头部），其余地方引用它

最后一条是本仓实测出来的：schema 里写死的分档数量（A/B/C 三档多少篇）在首批落地后就与实际不符，而 skill 里的数字反而是对的——**同一事实写两处，必有一处先烂**。

## 10. 最小清单（照着勾）

- [ ] 建目录：`wiki/` + `index.md` + `log.md` + `sources/` + `concepts/` + `tools/`
- [ ] 写 `index.md` 骨架，含 `<!-- wiki-index:auto-end -->` 与两个手写段标题
- [ ] 写 `log.md` 头，确定 op 白名单
- [ ] 写 schema（六节），先 150 行
- [ ] 放两个脚本，干跑一次确认能找到仓库根
- [ ] 选**最厚**的一篇 raw 做第一份 source 页（最厚的先做，暴露问题最多）
- [ ] 抽 2 个 concept，各落 3 条证据
- [ ] `--write` 重建 index → lint → 写第一条 log
- [ ] 再跑一次 index，确认 diff 为空
- [ ] 挑一个问题走一遍 query，确认 2 跳可达
